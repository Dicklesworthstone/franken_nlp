# `fnlp job`: stored-result management

This checkpoint connects the public command dispatcher to existing job storage
without enabling unqualified model discovery or inference. With the
`metadata-store` + `asupersync-runtime` Linux x86-64/AArch64 profile, the binary
registers `job status`, `job verify`, `job materialize`, and `job schema`.
The same shared dispatcher serves `fnlp` and `franken_nlp`. Other feature/target
graphs omit the command rather than presenting a success-shaped stub.

## Actual commands

Keep the original `JobLimits` as a JSON document in your job configuration.
The key file contains exactly the original 32 random bytes, not a password,
hex encoding or a caller label. It must satisfy the existing private-parent,
owner-only regular-file and no-symlink rules. `JOB_ID` below is the original
random job ID encoded as exactly 32 lowercase hex digits; it is not a content
hash or a value generated by this command.

```sh
fnlp job status \
  --job-dir /path/to/owned-job \
  --job-id "$JOB_ID" \
  --key-file /path/to/private-keys/job.key \
  --limits /path/to/original-job-limits.json \
  --memory-bytes 268435456 --json
```

Use the same arguments with `job verify` or `job materialize --ordered`.
Canonical JSON is the default; `--json` makes that selection explicit. No
original corpus, model, task defaults or inference recipe is required.
`job schema` describes this separate version-1 management interface and opens
no file or runtime. It does not silently revise the frozen `robot schema` v3.

`status` authenticates all stored metadata and the complete committed result
prefix before reporting metadata. A successful status operation may report
orphan-tail bytes, an interrupted stage or an unacknowledged output file; zero
exit means the inspection succeeded, not that those conditions are absent.
`verify` rejects tails/stages and checks an unacknowledged output against the
committed stream. `materialize` requires the entire job committed, verifies it,
and reuses the existing synced no-replace transaction to publish the fixed
`materialized.ndjson` inside the protected job. A matching file from a lost
publication acknowledgement can be reconciled without inference or rewriting
its contents. Unrelated existing output is never overwritten.

There are no `--key`/`--secret` bytes, model, arbitrary output, overwrite, purge,
repair or tail-discard options. No startup/resume inference commands are
registered by this checkpoint. Recovery that discards orphans and execution
resume still require the original explicit authenticated replay path.

## Process host and diagnostics

`NlpEngine::manage_owned_job` is the corresponding library method. Its
`StoredJobRequest` contains only protected existing-job access and one closed
operation. `JobManagementLimits` supplies the finite run budget and explicit
journal/serialization/IO RAM reservations. The method owns one existing
asupersync blocking/scoped invocation and process-ledger admission, without a
model or native KV allocation. Locked storage and key handles close before
physical completion; the returned metadata report keeps its output-memory
charge through caller serialization/delivery.

The CLI requires `--memory-bytes` as explicit whole-process authority. Defaults
for caller-modeled journal and serialization headroom are respectively
67,108,864 and 16,777,216 bytes and can be set with `--journal-memory-bytes` and
`--serialization-memory-bytes`. Metadata-index and bounded frame-buffer floors,
IO/path storage and report/cleanup reservations are additional. These values
are not measurements of fsqlite RAM or an allocator/RSS limiter. Inadequate
admission fails before opening job storage, rather than proceeding uncharged.

The default run limits are 300 seconds and 1,000,000 checkpoints, configurable
with `--max-seconds` and `--max-checkpoints`. They cover stored operations under
the host; the small bounded limits/key-file prelude is separate. Cancellation
is cooperative, not OS-I/O preemption. No new signal handler is installed.
An abrupt stop or lost return can follow durable publication; authenticate
stored state on the next invocation instead of treating an error as rollback.

Success prints one bounded canonical JSON metadata line to stdout, never the
private result stream. Failures print closed-code JSON to stderr and return the
existing exit code: 2 for usage, 4 for limits input, 5 for execution budget,
6 for cancellation, 7 for stored authentication/contract/integrity failures,
9 for admission or unsafe/busy storage, 10 for incomplete state/orphans, and
1 for other IO or uncertain-publication failures. Parser errors and invalid
argv never echo private values or paths. A broken output channel is terminal;
no second success record is appended. Publication is not undone because the
terminal summary could not be delivered.

Every report names `authenticated-stored-state-not-input-replay-v1`. This does
not verify a new corpus, infer missing results, establish numerical/model
quality, or grant permission to resume from stored hashes alone. Inspection
uses the ordinary fsqlite opener (including connection setup/rollback recovery),
not a forensic read-only mount. See `stored-job-management.md` for the exact
storage authority and threat boundaries.

## Validation boundary

Six host tests, ten command-contract tests, one root-registration test and three
compiled-binary integration tests accompany the connection. The binary tests
exercise actual no-model CLI status/verification/materialization, process-memory
refusal, private argv diagnostics and schema dispatch. None was executed here;
Rust compilation, controller DSR and platform crash/durability qualification
remain pending under `WIRING.md`. No feature graph, artifact or release gate was
promoted. Native `job start/resume`, persistent input spooling and external-sort
populations remain separate work.
